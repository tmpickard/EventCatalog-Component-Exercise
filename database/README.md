# Database design

The database is an independent development resource. The Express application
continues to use its in-memory services; this schema does not connect to or
change the Node.js application.

## Relationships

```text
users (1) ──< (many) events
users (1) ──< (many) event_registrations (many) >── (1) events
```

Each event has exactly one existing organizer. A user and an event can each
have many registration rows; the composite key on `event_registrations
(event_id, user_id)` permits a user to register for a particular event only
once.

## Identifiers and TypeScript

- User IDs are UUIDs, suitable for stable identifiers that can be generated
  independently of a database. The current backend creates string IDs such as
  `user_<uuid>`; database-backed code will transition to UUID strings
  (for example, `11111111-1111-4111-8111-111111111111`) and update its
  authentication/session lookups and API contracts. The current Node.js code
  is intentionally unchanged.
- Event IDs remain numeric to match the current TypeScript `Event.id: number`
  model. PostgreSQL generates them with a `BIGINT GENERATED ALWAYS AS IDENTITY`
  column. Consumers should treat the database ID as returned by the insert,
  never calculate a next ID themselves.
- The database `event_date` maps to the current model's ISO calendar-date
  string `date`. The database `organizer_id` maps to the backend model's
  `organizerId` after its identifier transitions from the `user_...` format to
  a UUID string. `created_at` and `updated_at` are persistence metadata not
  currently represented by the event TypeScript type.
- The database user columns map to the backend's `UserRecord` fields:
  `display_name` → `displayName`, `password_hash` → `passwordHash`, and
  `created_at` → `createdAt`. The database also stores `updated_at`, which the
  current user type does not yet expose.

## Integrity rules

### `users`

- The primary key guarantees unique user UUIDs.
- `email` is required and nonblank. The unique expression index on
  `lower(btrim(email))` prevents duplicate addresses regardless of letter case
  or leading/trailing whitespace.
- `display_name` and `password_hash` are required and cannot consist only of
  whitespace. The database stores a hash, never a plaintext password.
- Both timestamps are required and default to the transaction's current
  timestamp.

### `events`

- The identity primary key is generated by PostgreSQL.
- `organizer_id` is required and references `users.id`. `ON DELETE RESTRICT`
  rejects deletion of an organizer while any event references that user;
  events are not cascaded away.
- Name and location fields must be nonblank. The state value is a required
  two-character field.
- Capacity must be positive; registrations must be nonnegative and no greater
  than capacity. These `CHECK` constraints apply on both inserts and updates.
- Format is limited to `League`, `Tournament`, or `Casual`.
- `registered` defaults to zero. Creation and update timestamps default to the
  current timestamp. Automatic changes to `updated_at` on later updates are
  intentionally not implemented yet.

### `event_registrations`

- The composite primary key prevents duplicate registrations for the same
  event/user pair.
- Both foreign keys require an existing event and user and restrict deletion
  while a registration references either record.
- Capacity enforcement is deliberately not implemented. With concurrent
  requests, two transactions can both observe one remaining spot before either
  inserts its registration. Correct enforcement will need a concurrency-safe
  operation (for example, an atomic conditional capacity update or appropriate
  locking in a transaction), rather than a simple check followed by insert.

## Development data

`seed.sql` uses fixed UUIDs for its three fictional organizers and six
Pokémon-inspired community events. Its password hash values are generated from
discarded random bytes with Argon2id; there are no corresponding plaintext
passwords, so these development-only hashes cannot be used to log in. Rerunning
the seed updates the three fixed user records and skips an event when that
organizer already has an event with the same name. It does not wipe unrelated
development records or reset existing seeded event values.

`tests/integrity.sql` runs database-level positive and negative checks inside a
transaction and rolls all test data back. It expects `schema.sql` to have been
applied; it does not depend on seed data.

## Create and use a local database

The repository root README documents a PostgreSQL 17+ setup using a
`trainer_events_owner` schema/database owner and a separate, non-owner
`trainer_events_app` role. Create the empty `trainer_events_dev` database, then
apply `schema.sql`, `seed.sql`, and `tests/integrity.sql` as documented there.
No ORM, migration framework, Docker, or application database connection is
introduced in this exercise.
